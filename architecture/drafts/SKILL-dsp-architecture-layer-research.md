# Steps
1. Confirm the authorized read-only service source location and the separate overview architecture output directory. Never edit, fetch, pull, run migrations in, or regenerate service repositories. Do not deploy, publish, create infrastructure, send handoffs or save this skill globally without the required authorization. Do not copy secrets, connection values, user data or runtime logs.
2. Read the overview's current registration model/schema, Flow contract, architecture layer schema/addendum and one existing layer. Discover sanctioned documentation tools and fetch the requested Confluence pages. Search relevant service names/titles with CQL ordered by modification date; page through results if needed. Fetch promising pages fully before using them as evidence. If documentation is unavailable, record that limitation and do not invent it.
3. Record source provenance before synthesis: actual local commit if available (never fetch for it), otherwise per-file hashes and unknown freshness; Confluence numeric page IDs and returned versions. Record git status when possible or a before/after tree fingerprint if no .git exists. Use only already-authorized sources, no credentials/session inspection. If a preferred design tool is requested, attempt it, bound its runtime and report failures honestly.
4. Choose one existing Flow container with the clearest evidence for the first worked layer. Read its README, servicecatalog/docs, host entry/DI, handler registrations, feature/message contracts, storage and integration boundaries. Trace only enough to establish responsibilities and actual data/message paths; do not draw a call graph, retry internals, execution steps or implementation claims inferred only from DI/settings. Keep packages/external systems opaque when their sources were not examined.
5. Separate historical intent, desired features and upstream analysis from present local implementation. Mark disagreements explicitly. A Confluence ADF/ERP design does not establish an in-process component. Prefer direct source for present-code explanations without claiming it matches deployed code. Use uncertain/inferred provenance and a rationale for unsupported gaps; omit unsupported details instead of making plausible ones up.
6. Author the small root layer and catalog first under the overview's layers directory. Use stable namespaced layer:/comp:/aedge: semantic IDs independent of labels/ports/classes/line numbers. Root flowRef must resolve to the actual container (and optional handler). Keep existing generated registrations byte-stable unless an additive field is explicitly in scope and generator-preserving tests are available.
7. Model useful responsibilities, contracts, stores and message/data/dependency relationships. Label boundary nodes outside the shown compute even if service-owned. Never expand an external system without researched evidence. All architecture edges are conceptual; do not join telemetry/activity, throughput or observed-event IDs to these edges. Every node/edge/layer needs reviewed source citations and an uncertainties array. Use portable repo refs, reviewed symbols/line notes, hashes or actual commit IDs, and canonical Confluence URLs/version numbers.
8. Add depth only when another useful evidence-backed explanation exists. Use one canonical parent per layer, one inside component opening each direct child, no authored duplicate child/breadcrumb lists. Roots bind to Flow; descendants inherit the root. Breadcrumbs are derived from parent traversal. Prevent dangling references, duplicate roots/openers, cross-project jumps and all navigation cycles. Conceptual dependency cycles are different and may be valid.
9. Validate all documents against the checked-in schema, then cross-document uniqueness, project/scope agreement, safe catalog paths, Flow binding, parent acyclicity, child opener ownership, local edge endpoints and reviewed citations. Include negative tests for a multi-level tree, dangling refs, cycles, duplicate IDs and traversal. Verify source hashes and no service-repo writes. Existing registrations must still validate and preserve hashes; Flow/activity/layout must remain separate and unchanged.
10. Deliver the contract and one worked layer promptly, with exact artifact paths, cited pages/versions, evidence gaps, verification results and a UI/developer read-contract proposal. Describe missing runtime tests honestly. Route implementation handoffs through the designated lead; do not deploy/publish. Continue other service layers only after this first slice; research subsequent repositories independently rather than copying assumptions.
